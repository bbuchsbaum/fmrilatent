# fmrilatent

## Purpose

R package for latent space representations of fMRI neuroimaging data.
Provides S4 classes (`LatentNeuroVec`) for memory-efficient storage and
manipulation of dimensionality-reduced brain data using matrix
factorization (basis x loadings). Integrates with the `neuroim2` package
for standard neuroimaging data structures.

The core idea: represent 4D fMRI data as `X = B * L' + c` where B is a
temporal basis, L is spatial loadings, and c is a voxel-wise offset.
This enables efficient PCA, ICA, wavelet, Slepian, HRBF, and other
decompositions.

## For AI Agents

### Working In This Directory

- Always run `Rscript -e "devtools::load_all()"` after modifying R
  source files
- Run `Rscript -e "devtools::document()"` after changing roxygen2
  comments (regenerates `man/` and `NAMESPACE`)
- Collation order in `DESCRIPTION` matters — `latent_handles.R` must
  load before `all_class.R`
- 2-space indent, snake_case for functions/objects
- S4 methods use `setMethod("generic", "Class", ...)` pattern
- roxygen2 comments for user-facing functions; use `@keywords internal`
  for private helpers
- Keep files ASCII; prefer pure functions; avoid side effects or hidden
  globals

### Testing Requirements

- Run `Rscript -e "devtools::test()"` before committing
- Full check: `Rscript -e "devtools::check()"`
- Tests use testthat edition 3: `tests/testthat/test-*.R`
- Use [`set.seed()`](https://rdrr.io/r/base/Random.html) for
  reproducible random data in tests

### Common Patterns

- **Handle pattern**: `BasisHandle`/`LoadingsHandle` defer
  materialization — `basis(x)` calls `materialize_basis()` only when
  needed
- **Spec pattern**: `spec_time_*()` / `spec_space_*()` create
  lightweight descriptors; [`encode_spec()`](reference/encode_spec.md)
  dispatches to builders
- **Lift pattern**: `lift(reduction, spec)` computes bases on coarsened
  graphs, lifts to ambient space
- **Registry**: Shared cache for materialized dictionaries, controlled
  by `options(fmrilatent.registry.enabled = TRUE/FALSE)`

## Dependencies

### Internal (neuroim2 ecosystem)

- `neuroim2` — Core neuroimaging types: `NeuroVec`, `NeuroSpace`,
  `LogicalNeuroVol`, `IndexLookupVol`
- `neurosurf` — Surface-based neuroimaging (optional, used in some
  spatial methods)
- `neuroatlas` — Atlas data (optional, used for Schaefer parcellations)
- `rgsp` — Graph signal processing (optional, used in Slepian/graph
  methods)

### External

- `Matrix` — Sparse/dense matrix classes (`dgCMatrix`, `dgeMatrix`)
- `Rcpp` / `RcppEigen` — C++ interop for performance-critical code
- `methods` — S4 class/generic/method infrastructure
- `crayon` — Colored terminal output for
  [`show()`](reference/show-methods.md) methods
- `digest` — Hashing for handle IDs

## Issue Tracking with Mote

This project uses **mote** for local issue tracking, path reservations,
notes, handoffs, and agent coordination. **Do not use beads (`bd`) in
this repo.** Mote issue IDs may still have `bd-...` prefixes; use those
IDs only with `mote` commands.

### Essential Commands

| Command | Purpose |
|----|----|
| `mote doctor` | Validate the local mote store |
| `mote actor show` | Confirm the current actor identity |
| `mote ready` | List tasks without blockers |
| `mote new "Title" -p 1 --tag <area>` | Create a task |
| `mote show <id>` | View issue details and history |
| `mote preflight --issue <id> --paths <path> ...` | Check reservation conflicts before editing |
| `mote begin <id> --paths <path> ... --note "starting"` | Claim work and reserve paths |
| `mote note <id> --kind progress "..."` | Record progress, decisions, or blockers |
| `mote done <id> --note "finished"` | Mark completed work done |
| `mote handoff <id> --to <actor> --note "..." --release` | Hand off unfinished work |
| `mote release <id>` | Release a claim when stopping without completion |
| `mote board` | Inspect active work and reservations |
| `mote who-has <path>` | Find the actor reserving a path |
| `mote inbox` | Check direct coordination messages |

### Critical Rules for Agents

1.  **Do not run `bd` commands**; `mote` is the tracker for this
    project.
2.  **Reserve before editing** with `mote preflight` and `mote begin`.
3.  If `mote preflight` or `mote begin` reports a conflict, inspect with
    `mote who-has <path>` and coordinate before editing.
4.  Record meaningful state changes with `mote note`.
5.  Never hand-edit `.mote/ops/*.json`; publish tracker changes through
    `mote`.

## Multi-Agent Coordination

Use **mote** as the primary coordination channel for local agents.
Reservations are advisory but must be respected.

- **Reserve before editing**:
  `mote preflight --issue <id> --paths <path> ...` followed by
  `mote begin <id> --paths <path> ...`
- **Release when done or stopping**: `mote done <id>`,
  `mote handoff <id> ... --release`, or `mote release <id>`
- **Check inbox**: `mote inbox`
- **Send direct messages**:
  `mote msg send --to <actor> --issue <id> --kind request "..."`

## Commit & PR Guidelines

- Commits: imperative, concise (e.g., “Add HRBF basis generator”, “Wire
  HRBF to LatentNeuroVec”)
- PRs: describe scope, note tests run, call out performance implications
- Link issues when available

## Landing the Plane (Session Completion)

When ending a work session, complete ALL steps:

1.  File issues for remaining work
    (`mote new "Title" -p 1 --tag <area>`)
2.  Run quality gates (`devtools::test()`, `devtools::check()`)
3.  Update issue status (`mote done`, `mote note`, or `mote handoff`)
4.  Release claims/reservations (`mote release` or handoff with
    `--release`)
5.  Push committed code with `git push`
6.  Provide handoff context for next session

**Work is NOT complete until `git push` succeeds.**
